I'll note what the note observes, then sharpen it (the model does infer a rule, just an unlicensed one), then the practical consequence.It's noting the **underdetermination problem in example-based specification**.

**The core claim:** a set of input→output pairs picks out a *mapping*, not a *reason*. Infinitely many rules pass through the same finite points. So when you teach by example, the learner has to guess which rule you meant — and the examples themselves can't tell it.

Take the note's own case:

```
0  → false
"" → false
```

Which rule is that?

- JS-style truthiness coercion
- "empty/zero value → false" (then `[]` → false? but in JS `[]` is truthy)
- Python falsiness (then `[]` → false, `0.0` → false)
- "this legacy API treats sentinel values as absent"
- "numbers and strings both collapse to bool in this schema"

All consistent. They diverge immediately on `"0"`, `[]`, `None`, `-1`, `"false"`, `NaN`. That divergence is the "X shifts slightly."

**One sharpening I'd add:** it's not that the model learns no *why*. It learns *a* why — it has to, to generalize at all — just an unlicensed one, inherited from its priors rather than from you. Which means the failure isn't blankness, it's confident wrong extension. The model fills in the rule it finds most natural, and you don't find out which rule that was until it's already applied it somewhere you care about.

**"No handle" is the good phrase.** A handle is something you can grip to *steer*. If the behavior is stored as a lookup table, the only correction available is adding more rows — patch per edge case, forever, with no transfer between patches. If the behavior is stored as a rule plus rationale, you can edit the rationale once and the whole boundary moves with it.

**The counter-pressure**, which the note doesn't mention: examples are precise where rules are vague. "Coerce falsy values" is ambiguous in a way `0 → false` isn't. Stated rules drift, over- and under-apply, and get lawyered. That's why examples got used in the first place.

So the practical resolution isn't rule-instead-of-examples, it's **rule + examples + the examples' job stated**: here's the principle, here are cases chosen to pin down where its edges fall, and here's *why this edge is where it is*. The examples anchor the rule's vagueness; the rationale lets you extrapolate past the examples. Each covers the other's failure mode.

The deeper version of the note: this is the distillation problem generally. Behavior transfers; the reason behind it doesn't, unless you transfer it on purpose.
